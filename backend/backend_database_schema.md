# Backend Database Schema

## Overview

This document defines the PostgreSQL database schema for the InnoTech Hub Attendance System.

The database schema serves as the authoritative reference for the application's persistent data model and supports all backend functionality described in the API Contract and Business Rules.

The schema is designed to support:

- User authentication and authorization
- Event management
- Attendance lifecycle management
- Continuous presence monitoring
- Emergency ticket workflow
- Volunteer participation restrictions
- Notification management
- Activity history
- Audit logging
- Administrative reporting

All schema changes must be implemented through Alembic migrations to ensure consistent database versioning across development, testing, and production environments.

This document describes:

- Database entities
- Relationships
- Constraints
- Indexes
- Enumerations
- Migration strategy
- Performance considerations

--
```
## Design Principles

The database schema follows the principles below.

### Normalization

Data is normalized to reduce duplication while maintaining efficient query performance.

Related information is stored in separate tables and connected through foreign key relationships.

---

### Referential Integrity

Foreign key constraints enforce valid relationships between entities.

Database-level constraints prevent orphaned records and maintain data consistency.

---

### UUID Primary Keys

Every major entity uses UUID version 4 as its primary key.

UUIDs provide globally unique identifiers suitable for distributed systems while avoiding predictable sequential identifiers.

---

### Server-Managed Timestamps

Creation and update timestamps are generated by the backend using server time.

Client devices are not considered authoritative for persistence timestamps.

---

### Immutable Historical Data

Historical records such as:

- Activity History
- Audit Logs
- Presence Logs

are append-only.

Historical records must never be modified after creation.

---

### Business Logic Separation

The database is responsible for:

- Data integrity
- Constraints
- Relationships
- Indexes

Business workflows and validation logic remain the responsibility of the backend service layer.

---

### Backward-Compatible Migrations

Schema evolution must occur through Alembic migrations.

Existing production data must remain valid after every migration unless an explicitly approved migration strategy specifies otherwise.

# users

## Purpose

Stores all authenticated users of the system.

A user may be either an administrator or a volunteer (member).

Users are responsible for authentication, event participation, administrative operations, and system auditing.

---

## Table Definition

| Column | Type | Nullable | Default | Description |
|----------|------|----------|----------|-------------|
| id | UUID | No | uuid_generate_v4() | Primary key |
| full_name | VARCHAR(255) | No | — | User's full name |
| email | VARCHAR(255) | No | — | Unique email address |
| password_hash | VARCHAR(255) | No | — | Hashed password |
| role | user_role | No | MEMBER | User role |
| created_at | TIMESTAMPTZ | No | NOW() | Account creation timestamp |
| updated_at | TIMESTAMPTZ | No | NOW() | Last update timestamp |

---

## Constraints

- Primary Key (`id`)
- Unique (`email`)
- `role` must use the `user_role` enum.

---

## Relationships

One user may:

- create multiple events;
- participate in multiple attendance records;
- submit multiple emergency tickets;
- receive multiple notifications;
- generate multiple activity history records;
- perform multiple administrative actions recorded in audit logs.

---

## Indexes

| Index | Purpose |
|---------|----------|
| idx_users_email | Fast authentication lookup |
| idx_users_role | Filter users by role |

---

## SQL Definition

```sql
CREATE TABLE users (
    id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),

    full_name VARCHAR(255) NOT NULL,

    password_hash VARCHAR(255) NOT NULL,

```sql

    id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),

    title VARCHAR(255) NOT NULL,

    description TEXT,

    start_time TIMESTAMPTZ NOT NULL,

    end_time TIMESTAMPTZ NOT NULL,

    grace_period_minutes INTEGER NOT NULL DEFAULT 10,

# attendance_records

## Purpose

Stores the attendance lifecycle for a volunteer participating in an event.

An attendance record is created when a volunteer successfully checks in and remains the primary record for tracking attendance, presence monitoring, emergency requests, and check-out until the event is completed.

Each volunteer may have only one attendance record for a given event.

---

## Table Definition

| Column | Type | Nullable | Default | Description |
|----------|------|----------|----------|-------------|
| id | UUID | No | uuid_generate_v4() | Primary key |
| event_id | UUID | No | — | Associated event |
| user_id | UUID | No | — | Volunteer |
| check_in_time | TIMESTAMPTZ | No | NOW() | Check-in timestamp |
| check_out_time | TIMESTAMPTZ | Yes | NULL | Check-out timestamp |
| check_in_latitude | DOUBLE PRECISION | No | — | Latitude recorded during check-in |
| check_in_longitude | DOUBLE PRECISION | No | — | Longitude recorded during check-in |
| gps_accuracy_meters | DOUBLE PRECISION | No | — | GPS accuracy reported by the device |
| check_in_photo | VARCHAR(500) | No | — | Stored check-in photo reference |
| attendance_status | attendance_status | No | PRESENT | Final attendance status |
| current_presence_state | presence_state | No | CHECK_IN | Current presence monitoring state |
| attendance_duration_minutes | INTEGER | Yes | NULL | Calculated attendance duration |
| created_at | TIMESTAMPTZ | No | NOW() | Record creation timestamp |
| updated_at | TIMESTAMPTZ | No | NOW() | Last update timestamp |

---

## Constraints

- Primary Key (`id`)
- Foreign Key (`event_id`) → `events(id)`
- Foreign Key (`user_id`) → `users(id)`
- One attendance record per volunteer per event
- `attendance_duration_minutes` must be greater than or equal to zero when present

---

## Relationships

Each attendance record:

- belongs to one event;
- belongs to one volunteer;
- may contain many presence log entries;
- may contain multiple emergency tickets;
- may generate multiple notifications;
- may generate multiple activity history records;
- may generate multiple audit log entries.

---

## Indexes

| Index | Purpose |
|---------|----------|
| idx_attendance_event | Attendance lookup by event |
| idx_attendance_user | Volunteer attendance history |
| idx_attendance_status | Reporting |
| idx_attendance_presence_state | Active monitoring |
| idx_attendance_check_in | Chronological queries |

---

## SQL Definition

```sql
CREATE TABLE attendance_records (

    id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),

    event_id UUID NOT NULL REFERENCES events(id) ON DELETE CASCADE,

    user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,

    check_in_time TIMESTAMPTZ NOT NULL DEFAULT NOW(),

    check_out_time TIMESTAMPTZ,

    check_in_latitude DOUBLE PRECISION NOT NULL,

    check_in_longitude DOUBLE PRECISION NOT NULL,

    gps_accuracy_meters DOUBLE PRECISION NOT NULL,

    check_in_photo VARCHAR(500) NOT NULL,

    attendance_status attendance_status NOT NULL DEFAULT 'PRESENT',

    current_presence_state presence_state NOT NULL DEFAULT 'CHECK_IN',

    attendance_duration_minutes INTEGER,

    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),

    updated_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),

    CONSTRAINT uq_attendance_event_user
        UNIQUE (event_id, user_id),

    CHECK (
        attendance_duration_minutes IS NULL
        OR attendance_duration_minutes >= 0
    )
);

CREATE INDEX idx_attendance_event
ON attendance_records(event_id);

CREATE INDEX idx_attendance_user
ON attendance_records(user_id);

CREATE INDEX idx_attendance_status
ON attendance_records(attendance_status);

CREATE INDEX idx_attendance_presence_state
ON attendance_records(current_presence_state);

CREATE INDEX idx_attendance_check_in
ON attendance_records(check_in_time);
```

---

## Lifecycle

An attendance record progresses through the following lifecycle.

```
CHECK-IN

↓

Presence Monitoring

↓

Boundary Exit(s)

↓

Return(s)

↓

Emergency Ticket(s) (if required)

↓

Check-Out

↓

Attendance Completed
```

The attendance record remains the primary entity throughout the volunteer's participation in the event.

---

## Notes

- Attendance records are created only after a successful check-in.
- Presence monitoring begins immediately after attendance creation.
- Check-out updates the existing attendance record rather than creating a new record.
- Presence history is stored separately in the `presence_logs` table.
- Emergency requests are stored separately in the `emergency_tickets` table.
- Notifications, activity history, and audit logs reference this attendance record where applicable.

## Recorded Presence States

A presence log is created whenever one of the following states occurs.

| Presence State | Description |
|----------------|-------------|
| CHECK_IN | Volunteer successfully checked in |
| PRESENCE_OK | Volunteer confirmed inside the configured event boundary |
| LEFT | Volunteer exited the configured event boundary |
| RETURNED | Volunteer re-entered the configured event boundary |
| CHECK_OUT | Volunteer completed attendance |

---

## Notes

- Presence logs are append-only.
- Existing records must never be updated or deleted through the application.
- Presence logs represent the complete historical timeline of volunteer presence.
- The current volunteer state is stored in `attendance_records.current_presence_state`.
- Presence logs are used by reporting, activity history, and audit processes.

# emergency_tickets

## Purpose

Stores emergency requests submitted by volunteers during an active attendance session.

An emergency ticket is created when a volunteer requests permission to leave the event due to an emergency or official reason. Administrators review the request and either approve or reject it.

Multiple emergency tickets may exist for a single attendance record, allowing volunteers to submit new requests if previous ones are rejected or circumstances change.

| event_id | UUID | No | — | Associated event |
| user_id | UUID | No | — | Volunteer who submitted the request |
| reason | TEXT | No | — | Emergency reason provided by the volunteer |

## Constraints

- Foreign Key (`event_id`) → `events(id)`
- Foreign Key (`user_id`) → `users(id)`
- Foreign Key (`reviewed_by`) → `users(id)` (nullable)

---

## Relationships

Each emergency ticket:

- belongs to one attendance record;
- belongs to one event;
- belongs to one volunteer;
- may be reviewed by one administrator.

# volunteer_blocks

## Purpose

Stores temporary participation restrictions placed on volunteers by administrators.

A volunteer block prevents a volunteer from joining future events until the restriction is removed. Blocks are created based on administrative decisions, such as repeated policy violations, misuse of emergency requests, or other attendance-related issues.

Volunteer blocks maintain a complete history of restrictions for auditing and reporting.

---

## Table Definition

- Foreign Key (`template_id`) → `activity_templates(id)`
- `display_order` must be greater than zero.

---

## Relationships

Each template item:

- belongs to one template.

One template may contain multiple template items.

---

## Indexes

| Index | Purpose |
|---------|----------|
| idx_template_items_template | Template lookup |
| idx_template_items_order | Ordered activity retrieval |

---

## SQL Definition

```sql
CREATE TABLE activity_template_items (

    id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),

    template_id UUID NOT NULL
        REFERENCES activity_templates(id)
        ON DELETE CASCADE,

    title VARCHAR(255) NOT NULL,

    description TEXT,

    category VARCHAR(100) NOT NULL,

    priority activity_priority
        NOT NULL DEFAULT 'MEDIUM',

    display_order INTEGER NOT NULL,

    created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),

    CHECK (display_order > 0)
);

CREATE INDEX idx_template_items_template
ON activity_template_items(template_id);

CREATE INDEX idx_template_items_order
ON activity_template_items(display_order);
```

---

## Notes

- Template items are copied when a template is applied.
- Template items are never linked to generated activities.
- Editing template items affects only future activities created from the template.
- Existing activities remain unchanged after template updates.

## Referential Integrity

The database enforces referential integrity using foreign key constraints.

Where appropriate:

- `ON DELETE CASCADE` is used when child records should be removed with the parent (for example, attendance records and presence logs).
- `ON DELETE SET NULL` is used when historical records should be preserved after the referenced entity is removed (for example, audit logs and notifications).

This strategy maintains historical data while preventing orphaned records.

# Overall Indexing Strategy

## Purpose

Indexes are used to improve query performance for the most common application operations, including authentication, event management, attendance tracking, presence monitoring, emergency ticket processing, notification retrieval, reporting, and administrative auditing.

Indexes are created on frequently searched, filtered, sorted, and joined columns to minimize query execution time while maintaining acceptable write performance.

---

## Indexing Principles

The database follows these indexing principles:

- Every table uses a UUID primary key index.
- Foreign key columns are indexed to optimize joins.
- Frequently filtered enum columns are indexed.
- Timestamp columns used for sorting and reporting are indexed.
- Unique constraints automatically create supporting indexes.
- Composite indexes are used where multiple columns are commonly queried together.

---

## Common Query Optimizations

Indexes are designed to optimize operations such as:

- User authentication by email.
- Upcoming event retrieval.
- Volunteer attendance lookup.
- Presence history retrieval.
- Pending emergency ticket review.
- Active volunteer restriction lookup.
- Notification timeline retrieval.
- User activity history.
- Administrative audit reporting.

- Activity lookup by event.
- Volunteer assignment lookup.
- Activity progress timeline retrieval.
- Evidence retrieval for administrative review.
- Pending activity review lookup.
- Activity template retrieval by event type.

---

## Performance Considerations

Indexes improve read performance but introduce additional storage and write overhead.

Only columns frequently used in filtering, sorting, joining, or uniqueness validation are indexed.

Additional indexes should be introduced only after evaluating production query patterns.

# Migration Strategy

## Purpose

Database schema changes are managed using Alembic migrations.

Each migration represents a single, version-controlled change to the database structure and can be applied consistently across development, testing, and production environments.

---

## Migration Principles

The migration strategy follows these principles:

- Every schema modification must be implemented through an Alembic migration.
- Existing migrations must never be modified after being committed.
- New schema changes require new migration files.
- Migrations should be reversible whenever practical.
- Production data must be preserved during schema updates.

---

## Version Control

Migration files are stored within the project's Alembic migration directory and tracked using Git.

Each migration includes:

- revision identifier;
- parent revision;
- upgrade operations;
- downgrade operations (where applicable).

---

## Backward Compatibility

Whenever possible, schema changes should be backward compatible.

Examples include:

- adding nullable columns;
- introducing new tables;
- adding new indexes;
- creating new enum values.

Breaking schema changes should be avoided unless absolutely necessary and must be accompanied by appropriate migration planning.

---

## Deployment

Database migrations should be executed before deploying a new application version.

Successful migration execution should be verified prior to enabling new application functionality.

---

# Phase 4 Database Extension

Phase 4 extends the existing database schema to support production hardening.

Rather than introducing new business entities, this phase adds operational capabilities that improve reliability, security, recoverability, and maintainability while preserving complete backward compatibility with Phases 1–3.

---

## 1 Objectives

The Phase 4 database extension introduces support for:

- centralized audit logging improvements;
- spoofing detection history;
- backup metadata;
- production operational monitoring;
- configurable data retention.

The Offline Synchronization queue is intentionally **not** stored in PostgreSQL. Pending offline operations remain the responsibility of the frontend using IndexedDB.

---

## 2 Audit Log Enhancements

The existing `audit_logs` table is extended to support richer auditing.

Additional information recorded for business-significant updates includes:

| Column | Type | Description |
|----------|------|-------------|
| previous_values | JSONB | Object containing values before the change |
| new_values | JSONB | Object containing values after the change |
| retention_until | TIMESTAMP | Optional retention expiration based on configured policy |

These additions allow administrators to understand exactly what changed without modifying historical records.

Audit logs remain immutable after creation.

Only business-significant actions are recorded.

Examples include:

- authentication
- attendance lifecycle
- activity management
- assignment changes
- review decisions
- administrator operations
- backup execution
- configuration changes

Routine internal database updates should not generate audit records.

---

## 3 Spoofing Events

A new table stores every detected spoofing event.

### Table: `spoofing_events`

| Column | Type | Description |
|----------|------|-------------|
| id | UUID | Primary key |
| attendance_id | UUID FK | Related attendance session (nullable when not applicable) |
| event_id | UUID FK | Related event |
| user_id | UUID FK | User involved |
| detection_type | VARCHAR | Detection category |
| confidence | DECIMAL | Detection confidence score |
| description | TEXT | Detection details |
| device_information | JSONB | Device metadata used during evaluation |
| location_snapshot | JSONB | GPS information captured during detection |
| created_at | TIMESTAMP | Detection timestamp |

Each suspicious event is stored independently.

Repeated suspicious behaviour is determined from accumulated historical events rather than a separate score table.

---

## 4 Backup Metadata

Production backup operations are tracked using metadata stored within PostgreSQL.

### Table: `backup_metadata`

| Column | Type | Description |
|----------|------|-------------|
| id | UUID | Primary key |
| backup_type | VARCHAR | Full, incremental, differential |
| started_at | TIMESTAMP | Backup start |
| completed_at | TIMESTAMP | Backup completion |
| status | VARCHAR | Pending, Running, Completed, Failed |
| verification_status | VARCHAR | Verification result |
| retention_until | TIMESTAMP | Configured expiration |
| initiated_by | UUID FK | Administrator (nullable for automated backups) |
| notes | TEXT | Additional information |
| created_at | TIMESTAMP | Record creation |

This table stores metadata only.

Actual backup files remain external to the application database.
